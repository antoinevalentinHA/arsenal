# NAS — événement `release_diff_partial`

## Contrats

- `outils_externes/nas_arsenal/diff/release_diff_mqtt.md` v1.0.1 → v1.1.0 : ajout de l'événement `release_diff_partial`, réservé aux runs `status=partial`, distinct de `release_diff_failed` désormais réservé exclusivement à `status=error`. Ajout du champ `rejection_summary` (`count` + `categories[]` dédupliquées) sur le run-summary (§5.3), le plan état (§7.2) et le plan événement (§8.3). `error_reason`/`error_detail` ne sont plus jamais présents pour `partial`. `rejection_summary` absent ou incohérent avec `count >= 1` est traité comme un run-summary malformé (`error_reason=last_run_malformed`), sans émission de `release_diff_partial`. `contract_version` passe à `1.1.0`.
- Correction documentée dans la révision : une implémentation antérieure du publisher produisait, en fallback pour `status=partial`, la valeur `anchor_rejected` — absente du vocabulaire contractuel de toute version antérieure du contrat. Le publisher réellement déployé n'implémente pas encore `release_diff_partial`/`rejection_summary` : il continue de produire `release_diff_failed` pour un run `partial`. Alignement runtime noté comme chantier séparé, hors périmètre de cette révision documentaire.
- `outils_externes/nas_arsenal/diff/diff_release.md` : ajout de l'agrégation `rejection_summary` par run dans `release_diff_last_run.json` — porte exclusivement sur les rejets du run courant, jamais sur le ledger cumulé `rejected[]` de `state/processed_releases.json`. Le détail patrimonial des rejets (ancre, répertoire, date de détection) reste local à `processed_releases.json` ; seul le résumé agrégé traverse la frontière NAS → MQTT → Home Assistant.
- `contrats/arsenal_nas.md` v1.0.2 → v1.0.3 : vocabulaire événementiel aligné sur `release_diff_mqtt.md` v1.1.0 (§6, §7.2, §11) — `partial` n'est jamais interprété comme un échec d'exécution. Précision ajoutée : l'automation Home Assistant déployée n'écoute encore que `release_diff_failed` pour un run `partial` ; alignement runtime hors périmètre de cette révision.

# Navigation Lovelace — taxonomie des classes de dashboard

## Doctrine

- `ui/navigation.md` : ajout de la section 6 « Taxonomie des dashboards et Retour contextuel (Classes A–E) », issue de l'audit `audit_navigation_ui_lovelace.md`. Classe A (racine, exposée depuis Navigation, pas de Retour obligatoire), Classe B (sous-dashboard hiérarchique à parent unique, Retour obligatoire vers le parent déclaré), Classe C (facette latérale de domaine reliée par un bandeau, pas de Retour), Classe D (ressource partagée multi-parent, pas de Retour), Classe E (raccourci secondaire via `hold_action`/geste, ne crée aucune parenté). Interdiction explicite d'inférer la frontière Classe B/C par heuristique (absence d'exposition dans Navigation, nombre de prédécesseurs, asymétrie de badges, réciprocité d'un bandeau) : seule une déclaration explicite de l'intention architecturale fait foi. Sections renumérotées en conséquence (l'ancienne §6 devient §7, etc., jusqu'à l'ancienne §12 devenue §13).
- ajout de `ui/navigation_topology.yaml` : déclaration machine-readable de l'intention Classe B/C/D — `hierarchie` (mapping enfant → parent, 48 relations), `groupes_lateraux` (5 fichiers de bandeau : `aspirateur.yaml`, `ecs.yaml`, `imprimerie.yaml`, `meteo.yaml`, `voiture.yaml`) et `ressources_partagees` (`reglages-meteo-dashboard`, `meteo-backups-dashboard`).

## Checker

- `scripts/arsenal_contracts/check_lovelace_navigation_contracts.py` : ajout des règles R6 à R10 (toutes bloquantes), consommant `navigation_topology.yaml`. R6 valide la structure du fichier (clés attendues, doublons, dashboards/fichiers référencés réellement existants, non-chevauchement B/C/D). R7 vérifie que chaque enfant Classe B porte un Retour contextuel unique dont la cible résolue est le parent déclaré, et que ce parent navigue réellement vers l'enfant. R8 vérifie que les membres de chaque groupe Classe C ne portent aucun Retour contextuel dédié. R9 applique la même vérification d'absence de Retour aux ressources Classe D, indépendamment de leur nombre de prédécesseurs. R10 applique le sens inverse de R7 : tout Retour contextuel réellement surchargé en runtime doit être déclaré comme relation Classe B dans `hierarchie`, sinon erreur.
- ajout de `_StrictTopologyLoader`, loader YAML dédié à `navigation_topology.yaml` : une clé de mapping dupliquée lève une erreur au lieu d'être silencieusement écrasée par PyYAML.
- ajout de `primary_navigation_paths()` : exclut les sous-arbres portés par `hold_action` / `double_tap_action` (Classe E) du calcul des prédécesseurs utilisé par R7/R10.
- ajout des selftests R6 à R10, incluant un cas dédié à la régression « Retour supprimé sans reclassification » (référence PR #828).

## Runtime

- `18_lovelace/dashboards/systeme/nas.yaml` : badges passés de `includes/badges/base.yaml` à `includes/badges/diagnostics_systeme.yaml`, qui ajoute le bouton Retour vers `/system-dashboard` — réalise la relation Classe B déclarée `nas-dashboard: system-dashboard`.
- `18_lovelace/dashboards/meteo/meteo_temperature_min_max.yaml` : ajout du bouton Retour (`bouton_retour_badge_carre`) vers `/meteo-temperature-dashboard`.
